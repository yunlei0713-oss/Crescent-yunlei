# 墨巡（MoXun）UI / UX 审查与优化提示词

> 目标项目：/Users/xusong.yu/Desktop/moxun-test  
> 任务性质：基于现有产品进行视觉审美、交互体验和界面质量优化；不是重新开发，也不是增加功能。  
> 执行方式：必须使用全局安装的 `$ui-ux-pro-max` Skill。

## 一、任务目标

请你作为资深桌面端产品设计师与 Electron / React 前端工程师，对墨巡进行一次有证据、有取舍、可验收的 UI / UX 审查和优化。

核心目标：

1. 提升整体视觉审美、专业感、完成度和品牌辨识度，消除粗糙、临时拼凑或明显的 AI 模板感。
2. 优化信息层级、字体、字号、行高、留白、对齐、密度、颜色、边框、图标和动效。
3. 优化实际操作体验：导航是否清楚、状态是否易懂、常用操作是否顺手、反馈是否及时、键盘操作是否完整。
4. 保持运维工作台应有的高信息密度、稳定性和可读性，不要为了视觉效果牺牲操作效率。
5. 以现有代码和组件为基础做减法、整理和打磨。优先修复真实问题，不要为了体现工作量而大改。

**不要只输出审查报告或设计建议。** 完成只读审查后，直接实施明确、低风险且符合现有产品方向的优化，并进行真实运行验证。若发现需要改变品牌方向、产品信息架构或核心交互的重大决策，先说明证据和影响，等待我确认，不要擅自决定。

## 四、墨巡不可随意改变的产品与品牌基线

### 4.1 品牌方向

墨巡已正式定稿为**黑白水墨群山 + 蜿蜒河流**。品牌规范以 `Document/new/brand/brand-guide.md` 为准。

- 主视觉使用墨黑、深灰、淡墨灰、宣纸白和留白。
- 保留已批准的山峰与河流构图、现有 Logo、图标和品牌资源。
- 不重新设计品牌，不生成另一套图标，不重新发明 Logo。
- 禁止恢复旧 Crescent 月亮/月牙；禁止墨滴、圆环、巡检轨道、节点等废弃方向。
- 不使用蓝紫霓虹、青绿色科技节点、金色装饰、无意义渐变或传统古风装饰。
- 不要把山水图作为终端、日志、代码、Diff、表格或输入文字的背景。

### 4.2 主题系统

只保留并正确支持现有两套主题：

- `ink-wash-light`：墨巡 · 宣纸
- `ink-wash-dark`：墨巡 · 夜墨

必须沿用现有 CSS Variables、主题定义、持久化和 `useAppTheme()` / `subscribeAppTheme()` 机制。

- 不另建并行主题系统。
- 不在组件中散落硬编码颜色。
- 不新增第三套主题，不随意改变默认主题和迁移逻辑。
- 主题切换不能重建 PTY、iTerm 会话或其他运行状态。
- 终端、代码、日志、Diff、表格始终保证高对比度和纯色背景。

如发现 `.cursor/rules/development-standards.mdc` 中的强调色约定与品牌/主题规范、当前运行 Token 存在冲突，先核实实际使用位置和来源，记录冲突与影响；不得擅自引入新的青绿装饰色，也不得未经核实大面积替换语义状态色。

### 4.3 产品布局与交互

`Document/UI_DESIGN_SYSTEM.md` 是当前 UI 规则的重要来源，必须完整阅读。重点保持：

- 墨巡是紧凑、对话优先的桌面运维协作台；聊天是唯一主工作区。
- iTerm 是外置人工操作界面，不要重新引入内嵌终端画布、终端标签栏、子终端面板或分屏工作区。
- 保留现有侧栏折叠/展开、会话归档、终端管理、设置子菜单和导航约定。
- 保留当前消息阅读宽度、输入区宽度、固定输入区、独立正文滚动和窄窗口适配规则。
- 保留已完成的对话定位条、消息辅助信息、思考/工具详情折叠、行内代码换行、建议区和错误详情等交互。
- 不恢复重复标题、结果卡片、嵌套卡片、无意义欢迎图、全屏装饰背景。
- 交互不能只依赖 hover；键盘焦点、Escape、无障碍名称和无 hover 设备必须可用。
- 重要状态不能只靠颜色表达；错误、警告、成功应保留语义和文字/图标提示。

## 五、优化范围与禁止事项

### 允许优化

- Renderer 页面和组件的视觉层级、排版、间距、对齐、尺寸、密度。
- 现有 CSS / Tailwind 样式和主题 Token 的合理复用、重复样式收敛。
- 已有组件的交互反馈、空状态、加载态、错误态、禁用态、焦点态和响应式细节。
- 现有图标的语义准确性、尺寸、线宽和一致性（优先使用已安装的 `lucide-react`）。
- 现有动效的节奏、性能和减少动态效果支持。
- 现有组件的轻量拆分、样式整理和重复代码清理，但必须有实际收益。

### 不允许擅自做

- 不增加新功能、新页面、新模块、新工作区或新的产品概念。
- 不为了视觉丰富而添加仪表盘、统计卡片、欢迎页、装饰图表、渐变背景或多余卡片。
- 不大规模重写组件体系，不引入新的 UI 框架、图标库、动画库、字体依赖或 npm 包。
- 不修改 Pi Agent 行为、模型调用、SSH、MCP、终端权限、命令审批、Diff 审批、数据库结构、持久化协议或业务逻辑。
- 不改变 Main / Preload / Renderer 的 Electron 安全边界，不新增 IPC，不让 Renderer 获得 Node 或文件系统能力。
- 不修改应用标识、产品名称、品牌图标、签名、公证、打包架构和发布流程。
- 不删除用户数据、历史报告、截图或现有资源。
- 不清理、重置或覆盖已有未提交改动；不执行 `git reset`、`git checkout --`、`git clean` 等破坏性操作。
- 不创建 Git commit，不 push，不打包安装程序。

若某个视觉问题必须触及上述边界才能解决，先停止该项并报告，不要绕过限制。

## 六、执行流程

### 阶段 1：只读审查与建立基线

1. 执行 `git status --short`，记录已有工作区改动；所有已有改动均视为用户资产。
2. 读取项目规范、品牌规范、主题规范和最近的 UI 验收报告。
3. 识别项目实际技术栈、Renderer 页面结构、主题入口、组件复用关系和样式组织。
4. 启动当前 Electron 应用，检查实际界面；不能只靠阅读 JSX/CSS 推测视觉效果。
5. 覆盖主要现有场景：主聊天区、侧栏、输入区、消息/工具时间线、终端管理菜单、设置及已有的知识/Skills/MCP 等页面。
6. 分别检查浅色和深色主题，以及宽窗口和窄窗口。
7. 输出问题清单：问题、实际证据（文件/组件/截图/复现步骤）、影响、严重程度、建议方案、涉及范围。

先区分真实问题、个人偏好和已完成且正常的设计。不要把“与其他 AI 软件不一样”本身当成缺陷。

### 阶段 2：形成统一优化方向

基于 UI UX Pro Max 的检索结果和当前项目规范，提出一套简洁、可落地的优化方向：

- 视觉层级：主要内容、辅助信息、低频操作是否清楚。
- 字体排版：字体、字号、字重、行高、字距是否统一。
- 空间节奏：边距、间距、对齐、内容宽度和密度是否协调。
- 色彩体系：浅/深主题是否一致，语义色和品牌色是否混乱。
- 组件细节：按钮、输入框、菜单、弹窗、列表、徽标、分隔线是否统一。
- 交互体验：悬停、焦点、按下、禁用、加载、成功、失败等状态是否完整。
- 动效与性能：是否有多余动画、布局抖动、重渲染或明显延迟。
- 可访问性：键盘导航、焦点可见性、对比度、语义标签和减少动态效果。

不要把所有问题都升级成设计系统重构。优先选择收益高、风险低、改动小的项目。

### 阶段 3：实施优化

1. 先处理高收益、低风险的问题，再处理次要问题。
2. 每批修改聚焦一个区域，避免一次性大范围重写。
3. 复用现有组件和 Token；需要抽象时，必须证明存在真实重复或维护收益。
4. 维持现有业务行为、事件处理和状态流；视觉优化不能改变原交互语义。
5. 对可能影响布局、滚动、输入、键盘和主题切换的改动补充或更新回归测试。
6. 不要仅凭浏览器模拟或静态 HTML 判断 Electron 界面；应尽量使用项目实际 Electron Renderer 验证。

### 阶段 4：真实视觉验收与回归

必须完成实际运行验证，而不是只报告“代码已修改”。

至少检查：

- 浅色主题和深色主题。
- 1440 px 左右的常规桌面窗口。
- 800 px 左右的中等窗口。
- 560 px 左右的窄窗口（若系统最小窗口尺寸不允许，记录实际限制，不得伪称通过）。
- 聊天消息较长、工具调用较多、错误详情展开、输入区有附件等真实布局状态。
- 菜单、弹窗、输入框、列表、滚动、焦点、键盘操作和 Escape。
- 无横向溢出、遮挡、截断、文字重叠、布局跳动、输入区覆盖正文。
- 深浅主题的文本对比度和状态语义。
- `prefers-reduced-motion` 下动效行为。
- 常用操作不能因为视觉调整而增加不必要的点击次数。

使用当前 Electron 项目实际运行截图进行逐张检查。截图和结果保存到本轮独立验证目录，不覆盖 `Document/new4/` 中的历史证据。

### 阶段 5：测试与交付

按项目既有约定执行：

```bash
npm run ci
npm run test:local
```

如本轮改动范围需要，再运行相关定向测试和实际 Electron 交互验证。

- `npm run ci` 必须通过；如失败，修复本轮引入的问题并重跑。
- `npm run test:local` 按项目约定执行；测试跳过项要明确列出原因，不能将 skipped 统计为 passed。
- 不提交本地测试文件；遵守 `Document/TESTING.md`。
- 不创建安装包，不提交 Git。

在 `Document/new5/` 下生成实施报告，至少包括：

1. 审查范围和实际基线。
2. 问题清单及优先级。
3. 使用了哪些 UI UX Pro Max 检索、采用了哪些建议、舍弃了哪些建议及原因。
4. 设计决策与现有品牌/主题规范的对应关系。

6. 浅色/深色及不同窗口尺寸的实际截图。
7. CI、定向测试、全量本地测试结果。
