# 1. 项目目标与产品定位

## 1.1 改造背景

此前 Agent 拥有较大的系统操作权限，能够通过终端工具自动输入和执行命令。由于模型判断、上下文理解或工具调用可能出现偏差，不恰当命令可能影响生产环境。

本次改造不再依赖提示词、命令风险等级、普通确认弹窗或可切换的安全模式来约束 Agent。必须从工具注册、Main Process 权限边界和 IPC 调用链上彻底取消 Agent 的终端执行能力。

新的产品定位：

**墨巡是一款由 AI 提供分析、诊断、知识支持和操作建议，由人类掌握实际操作权的智能运维协作平台。**

Agent 应像经验丰富的运维工程师或老师：

1. 理解用户描述的问题。
2. 分析现有终端、日志、配置文件和图片。
3. 判断当前最需要确认的事项。
4. 一次给出一个明确的操作建议。
5. 用户亲自输入命令。
6. Agent 观察输入和执行结果。
7. 根据真实结果决定下一步。
8. 用户可以随时提问、纠正判断、改变排查方向或结束会话。

## 1.2 五大改造目标

| 优先级 | 方向 | 目标 |
|---|---|---|
| P0 | 全局权限重构 | Agent 永远无法执行终端命令 |
| P0 | Guided Ops | 人工输入、Agent 观察、逐步指导 |
| P1 | 本地文件审批 | 文件创建、修改、删除必须经人工审批 |
| P1 | 多模态输入 | 图片、文本、日志、配置真正进入模型 |
| P1 | 品牌与 UI | 更名墨巡、新图标、移除 GitHub 外链、水墨主题 |

P0 是交付门槛。P0 未通过安全测试，不得进入正式发布。

## 1.3 明确不做的事情

- 不恢复 Agent 自动执行命令能力。
- 不新增可切换的“自动执行模式”。
- 不允许子 Agent 或 MCP 绕过主 Agent 权限。
- 不通过隐藏按钮代替底层权限控制。
- 不在本轮擅自更换应用 Bundle Identifier。
- 不连接生产集群验证功能。
- 不因品牌重塑而删除历史会话、知识库、SOP 或用户配置。

# 2. 全局安全架构：Agent 永久失去终端执行权

这是整个项目优先级最高的工作。

## 2.1 不可变安全原则

**Agent 可以读取、分析、建议，但不能执行终端命令。**

该限制对以下所有主体生效：

- 主 Agent。
- 子 Agent、临时 Agent、后台 Agent。
- 所有 Agent Style。
- 所有模型供应商。
- 所有会话和历史会话。
- MCP 工具。
- 变更计划。
- 脚本执行器。
- 子终端和远程终端。
- 所有间接命令执行入口。

不得存在通过切换模式、修改 Prompt、重新创建会话、重新加载 Runtime 或修改普通设置恢复执行能力的入口。

## 2.2 权限矩阵

| 操作 | 权限 |
|---|---|
| 读取本地文件、代码搜索 | 允许 |
| 读取终端上下文 | 允许 |
| 观察用户手动输入和终端输出 | 允许，须脱敏 |
| 提供命令建议 | 允许 |
| 复制命令到剪贴板 | 允许 |
| Agent 自动输入终端 | 永久禁止 |
| Agent 自动执行命令或脚本 | 永久禁止 |
| Agent 自动确认终端提示 | 永久禁止 |
| Agent 远程部署、重启、修改服务 | 永久禁止 |
| 创建本地文件 | 必须审批 |
| 修改本地文件 | 必须审批 |
| 覆盖、删除本地文件 | 单独强审批 |
| MCP 只读操作 | 审核后允许 |
| MCP 写入、执行、部署、远程控制 | 禁止 |

文件审批与终端执行是两套独立权限。批准本地文件修改绝不意味着授予终端权限。

## 2.3 当前代码审查已知入口

以下是初步定位，Codex 必须重新检查当前分支和调用关系：

- src/main/agent/pi-host.ts
- src/main/agent/pi-terminal-bash.ts
- src/main/agent/pi-subagent.ts
- src/main/agent/pi-change-plan.ts
- src/main/agent/pi-mcp-tools.ts
- src/main/agent/mcp-approval.ts
- src/shared/approval-policy.ts
- src/shared/agent-types.ts

此前审查发现的风险线索：

1. pi-host.ts 的默认工具列表注册了 bash。
2. planned 模式可能暴露 bash、read、return_to_main_terminal、submit_change_plan 等工具。
3. immediateTools 可能继承当前会话工具。
4. pi-subagent.ts 会重新创建 ptyBashTool 并通过 customTools 注册。
5. pi-terminal-bash.ts 存在 PTY 命令执行能力。
6. approval-policy.ts 的旧策略仍包含静态只读命令判断，但这不应成为 Agent 终端权限的基础。
7. 变更计划和 MCP 可能形成间接执行路径。

## 2.4 建立独立 Agent Capability Policy

建议增加统一的能力策略，例如：

- terminal.read
- terminal.observe
- terminal.suggest
- file.read
- file.search
- file.write.request
- file.write.approve
- mcp.read

Agent 能力中不得存在 terminal.execute、terminal.write、shell.exec、pty.write 等权限。

策略采用默认拒绝：只有明确登记、完成审查的能力才可使用。

要求：

1. 工具注册阶段过滤不允许的工具。
2. Agent Runtime 初始化时执行权限断言。
3. Main Process 对 Agent 来源的执行请求进行二次拒绝。
4. IPC 必须区分 user-originated 与 agent-originated 请求。
5. 不能信任 Renderer 传来的 actor 字段；调用来源必须由可信 IPC 上下文或 Main Process 会话状态确定。
6. 不允许 Agent 伪造用户身份。
7. 旧会话恢复时不得重新加载旧 bash 工具。
8. Prompt 仅负责行为引导，不承担安全边界。

注意：普通用户通过 xterm 手动输入命令时，仍然允许正常写入 PTY。不得误伤用户自己的 SSH、sudo、vim、mysql、psql 等交互。

## 2.5 全面排查命令执行链

逐一搜索并审计：

- executeCommandInTerminal
- pty.write
- session.write
- terminal:write
- bash / shell 工具
- 脚本执行器
- child_process / spawn / exec
- MCP 命令执行
- 子终端
- 外部进程启动
- 变更计划执行器
- 快捷键和菜单触发路径
- 自动化任务、后台任务和重试路径

不能只删除 pi-host.ts 中的 bash 注册。必须追踪所有工具调用、IPC、Main Process 和底层执行函数。

底层 PTY 仍然保留给用户手动操作。安全重构的目标是切断 Agent 到 PTY 写入的调用路径，而不是删除终端本身。

## 2.6 子 Agent 与多 Agent

- 删除子 Agent 的 bash 和终端写入工具。
- 子 Agent 只能使用主 Agent 审核后的只读白名单。
- 子 Agent 不得自行创建更高权限 Agent。
- Agent-to-Agent 委派不得提升权限。
- 后台任务、摘要任务和重试任务继承相同权限。
- 每次创建 Runtime 都重新执行能力断言。

## 2.7 变更计划转型

检查 pi-change-plan.ts 及相关执行模块。

变更计划只允许：

- 生成操作步骤。
- 解释命令用途。
- 分析风险和前置条件。
- 给出备份、回滚和验证建议。
- 等待用户手动执行。
- 根据用户提供的结果更新步骤状态。

取消自动执行检查、自动备份、自动变更、自动回滚和批量命令派发。

## 2.8 MCP 工具审查

必须根据真实实现和副作用分类，不得根据工具名称或描述判断。

| 类型 | 处理 |
|---|---|
| 监控指标查询、日志读取 | 审查后允许 |
| 配置读取、代码搜索 | 允许 |
| 数据库只读查询 | 审查后允许 |
| 数据库写入 | 禁止 |
| 远程命令执行 | 禁止 |
| 服务重启、部署 | 禁止 |
| 远程文件修改、上传 | 禁止 |
| 远程控制、网络写入 | 禁止 |

未审查工具默认拒绝。对每个工具检查其内部是否调用 shell、远程 API 写入、文件上传或其他副作用接口。建立可重复执行的 MCP 审计清单和测试。

# 3. 本地文件审批系统

## 3.1 设计目标

Agent 可以读取、搜索和分析本地文件。Agent 需要创建或修改本地文件时，必须先提交明确的变更申请，由用户批准后才可写入。

本地文件修改不能通过终端命令实现，必须使用独立的文件写入服务。

## 3.2 操作规则

| 操作 | 审批要求 |
|---|---|
| 读取、搜索 | 直接允许 |
| 创建文件 | 人工批准 |
| 修改文件 | 人工批准 |
| 批量修改 | 展示全部文件 Diff 后批准 |
| 覆盖文件 | 单独强审批 |
| 删除文件 | 单独强审批 |
| 移动或重命名 | 人工批准 |
| 修改目录结构 | 人工批准 |

## 3.3 审批流程

1. Agent 生成修改申请。
2. Main Process 规范化目标路径并生成 Diff。
3. Renderer 展示完整差异、理由和风险。
4. 用户批准、拒绝或要求重新调整。
5. Main Process 验证审批凭据、路径、操作和内容 Hash。
6. 执行精确写入。
7. 重新读取文件并验证写入结果。
8. 记录审批和实际变更审计事件。

## 3.4 安全约束

- 审批绑定精确路径、操作类型、原始 Hash 和新内容 Hash。
- 审批是一次性的，不能复用。
- 审批必须设置有效期。
- 文件内容或 Diff 变化，审批自动失效。
- 文件在审批期间发生变化，审批自动失效。
- 规范化路径，防止路径穿越。
- 检查符号链接，防止越权写入。
- Agent 不能扩大已批准的文件范围。
- 批量变更必须完整展示每个文件的 Diff。
- 删除和覆盖必须单独确认。
- 写入失败不得报告成功。
- 写入后必须重新读取校验。
- 重要文件提供备份或回滚方案。
- Main Process 验证审批；Renderer 不能自行决定写入。

## 3.5 审批界面

展示：

- 文件路径。
- 操作类型。
- 修改原因。
- 原始内容和新内容。
- 完整 Diff。
- 风险等级。
- 备份与回滚方案。

操作按钮：

- 批准本次修改。
- 拒绝。
- 要求 Agent 重新调整。
- 查看完整文件。

禁止提供永久授权、以后都允许等选项。

# 4. Guided Ops：教学式运维工作流

## 4.1 交互目标

把原有 Agent 自主执行型交互改造成逐步指导型交互。

核心流程：

**用户提出问题 → Agent 分析 → 提供一个操作建议 → 用户手动执行 → Agent 获取结果 → 分析 → 下一步建议。**

Agent 不应一次生成十几条命令让用户自行执行。默认一次只提供当前最有价值的一步。

## 4.2 状态机

建议状态：

| 状态 | 含义 |
|---|---|
| ANALYZING | 分析问题和现有证据 |
| PROPOSAL_READY | 已生成一条建议 |
| WAITING_OPERATOR | 等待用户手动操作 |
| COMMAND_RUNNING | 观察到用户已提交命令 |
| OBSERVING | 采集终端输出 |
| EVIDENCE_READY | 整理执行结果 |
| ANALYZING_NEXT | 分析下一步 |
| COMPLETED | 用户确认解决或结束 |
| INTERRUPTED | 用户改变方向或打断 |
| OBSERVATION_UNCERTAIN | 无法可靠判断命令边界或结果 |

状态转换必须由真实事件驱动。模型不能仅凭自己的文字声明某条命令已经执行或成功。

## 4.3 单步建议卡片

每次建议包含：

- 步骤编号。
- 当前判断。
- 排查目标。
- 建议命令。
- 执行位置和目标主机。
- 命令用途。
- 风险等级。
- 预期输出。
- 异常结果的下一步处理方式。

示例：

**第 1 步：检查磁盘空间**

当前判断：暂时不能确定是哪个挂载点导致磁盘空间不足，需要先获取磁盘使用情况。

建议命令：

    df -h

执行位置：当前 SSH 主机。

风险：只读查询。

预期结果：列出挂载点、总容量、已使用容量和使用率。

允许的交互：

- 复制命令。
- 询问 Agent。
- 跳过此步骤。
- 改变排查方向。

严禁出现：

- 自动执行。
- 发送到终端。
- 一键运行。
- 自动确认。

复制命令只能调用剪贴板 API，不得调用终端写入 API。

## 4.4 用户可随时打断和改变方向

支持自然语言指令：

- 先别查磁盘了，看看是不是 MongoDB。
- 我怀疑是网络问题。
- 解释一下这个命令。
- 这个命令会不会影响生产环境？
- 换一个更安全的查询方式。
- 暂时停止排查。
- 我想先查看另一台机器。

收到用户改变方向的消息后：

1. 停止当前 Agent 推理任务。
2. 保留此前已获得的证据。
3. 更新当前排查目标。
4. 不继续旧方向的建议。
5. 基于新方向重新分析。

允许查看历史步骤和证据。

## 4.5 Agent Style

保留 swift、concise、guided、teach 四种表达风格：

| 风格 | 行为 |
|---|---|
| Swift | 快速判断，每次一个建议 |
| Concise | 简短解释，一次一个建议 |
| Guided | 逐步协作，解释排查目标 |
| Teach | 详细讲解原理、风险和判断过程 |

所有风格必须服从同一全局权限策略。Style 只能控制表达方式，不能控制权限。

# 5. Terminal Observer：只读终端观察器

## 5.1 目标

Terminal Observer 只观察用户手动操作，不产生任何终端输入，不改变 PTY 行为，不自动注入辅助命令。

建议新增模块目录：

    src/main/terminal/observer/

职责：

- 观察用户输入。
- 识别命令提交边界。
- 采集命令输出。
- 识别命令完成状态。
- 关联终端、连接和主机身份。
- 对敏感信息脱敏。
- 向 Agent 提供结构化证据。

## 5.2 数据结构参考

    interface TerminalObservation {
      eventId: string
      tabId: string
      connectionId?: string
      sessionGeneration: number
      host?: string
      cwd?: string
      command?: string
      output?: string
      exitCode?: number
      startedAt?: number
      finishedAt?: number
      status:
        | 'submitted'
        | 'running'
        | 'completed'
        | 'failed'
        | 'interactive'
        | 'unknown'
      sensitive: boolean
      redacted: boolean
    }

最终类型必须适配现有 TypeScript 规范，不要求机械照搬。

## 5.3 输入采集

重点检查：

- src/renderer/src/hooks/useXtermLifecycle.ts
- src/main/terminal/ipc.ts
- xterm onData。
- terminal:write。
- 现有手动输入记录和输出缓冲区。

不能把原始键盘输入直接当作完整命令历史。

必须处理：

- 退格和方向键。
- 历史命令。
- 多行命令和多行粘贴。
- Tab 补全。
- Ctrl+C、Ctrl+D。
- sudo 和 SSH 密码。
- OTP。
- vim、less、top。
- mysql、psql。
- kubectl exec。
- 交互式 Shell。

## 5.4 命令边界识别

优先研究 Shell Integration 和可靠的命令开始、结束标记，例如 OSC 133。

要求：

- 有可靠标记时使用真实标记。
- 无可靠标记时可以记录用户提交内容，但状态标为不确定。
- 不得伪造退出码。
- 不得仅凭提示符出现就认定命令成功。
- 不得为了获取退出码向用户终端注入额外命令。
- 交互式程序期间暂停普通命令行解析。

## 5.5 敏感输入处理

遇到密码提示或不确定是否为敏感输入时：

- 暂停命令采集。
- 不记录密码。
- 不将原始输入发送给模型。
- 不写入长期审计记录。
- 不能确定内容安全时宁可不采集。

## 5.6 输出采集和故障隔离

复用现有终端输出缓冲区，重点检查：

- terminalOutputBuffers
- appendTerminalContext
- observeTerminalTransport
- terminal:get-context

观察器不得阻塞终端数据传输。

观察器异常时：

- 用户终端继续工作。
- SSH 连接继续工作。
- 用户可以继续输入。
- Agent 显示观察暂不可用。
- 不得丢弃用户正常输入。

## 5.7 主机身份绑定

每条证据必须关联：

- Terminal Tab。
- SSH Connection。
- Host。
- Session Generation。
- 工作目录。
- 采集时间。

切换主机、重连或终端重建后，旧上下文不能直接当成新主机结果。目标发生变化时，旧命令建议自动失效。

## 5.8 上下文长度

- 优先保留最近相关命令。
- 输出过长时保留错误、关键行和摘要。
- 不默认上传完整日志。
- 设置可配置上下文上限。
- 允许用户补充更多内容。
- 原始输出保留与否必须有明确的数据保留策略。

# 6. 多模态输入升级

## 6.1 当前已知问题

12. 只向模型传递完成当前分析所必需的上下文。

- 旧执行模式配置。
- 旧审批配置。

5. 品牌改名不能删除旧用户数据目录。
6. 默认保留 Bundle Identifier，除非有单独迁移方案。
7. 自动更新、签名和应用安装身份需单独评估。

# 20. 最终验收标准

## 安全

- Agent 无法执行任何终端命令。
- 主 Agent 和子 Agent 权限一致。
- MCP 无法绕过权限。
- 变更计划不再自动执行。
- 本地文件修改必须审批。
- 审批不可复用、不可扩大范围。
- 用户终端可以正常操作。

## 交互

- Agent 能读取用户手动输入的命令。
- Agent 能读取对应终端输出。
- Agent 能识别目标主机和会话。
- Agent 默认一次只提供一个当前操作步骤。
- 用户可以随时改变排查方向。
- Agent 根据实际结果继续分析。

## 多模态

- 可以拖入图片。
- 可以粘贴截图。
- 可以拖入日志和配置文件。
- 图片真实进入支持视觉的模型。
- 可以结合终端上下文进行分析。

## 品牌与视觉

- 应用名称统一为墨巡。
- 正式图标使用水墨群山与蜿蜒河流，不再使用月亮、墨滴或巡检环。
- macOS ICNS、Windows ICO、PNG 多尺寸、favicon 均完成验证。
- 横版/竖版 Logo 的浅色和深色版本均可用。
- GitHub 外链入口移除，更新机制不受误伤。
- 水墨山河主题提供宣纸浅色和夜墨深色两套完整 Token。
- 山水图只用于品牌展示区域，不干扰终端、代码、日志和 Diff。
- 主要工作区完成视觉统一，终端阅读体验不退化。

## 稳定性

- SSH 不受影响。
- PTY 不受影响。
- 模型调用不受影响。
- 知识库和 SOP 不受影响。
- 历史对话不丢失。
- macOS 本地运行通过测试。

# 21. 给 Codex 的最终执行指令

请将本计划作为墨巡本轮全面改造的正式需求基线。

严格按以下顺序执行：

**安全底座 → 文件审批 → 终端观察 → Guided Ops → 多模态 → 品牌与 UI → 全面测试。**

不要一开始同时修改所有模块。先完成 Phase 0，输出真实代码审查结果、调用链、安全缺口和任务拆分；随后逐阶段实施。

每个阶段必须：

1. 修改前明确影响范围。
2. 修改后运行对应测试。
3. 提供实际测试结果。
4. 检查已有功能是否退化。
5. 更新实施记录。
6. 发现安全问题立即停止相关阶段，不得带着安全缺口继续交付。

本次最重要的不是让 Agent 更会执行，而是让 Agent 更会分析、更会指导，同时在技术上彻底失去擅自操作生产环境的能力。

**最终产品原则：AI 负责思考，人负责决策；AI 提供建议，人负责执行；AI 分析结果，人掌握最终控制权。**
