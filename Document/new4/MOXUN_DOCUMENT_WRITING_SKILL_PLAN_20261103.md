> 范围：增加一个内置、自动触发的通用文档写作 Skill

## 1. 改造目标

给墨巡增加一个简单、固定的通用文档写作 Skill：**document-writing**。

用户提出文档撰写、整理、修改或排版需求时，墨巡自行识别并加载该 Skill。用户不需要知道 Skill 名称，也不需要输入“使用某某 Skill”等提示。

最终行为：

- 用户说“写一份 MongoDB 磁盘告警 SOP”，自动加载文档写作规范。
- 用户说“把这些聊天记录整理成技术方案”，自动加载。
- 用户说“修改这份方案，让结构更合理、排版更专业”，自动加载。
- 普通技术问答、终端运维、代码编写等非文档任务，不加载该 Skill。
- 默认使用用户当前语言；中文文档使用自然、准确、专业的中文表达。
- 默认输出 Markdown；只有用户要求 Word、PDF 等格式时，才使用墨巡已有的文件处理能力生成对应文件。

本轮只做这一项能力，不扩展成文档平台或多 Agent 写作系统。

## 2. 现有实现与改造边界

已检查的相关代码：

| 文件 | 当前职责 | 本轮使用方式 |
|---|---|---|
| `src/main/agent/pi-host.ts` | Agent 主运行入口，组装并提交每轮 Prompt | 在这里完成自动触发和内置 Skill 注入 |
| `src/shared/agent-run-prompt.ts` | `buildPromptText`、`buildActiveSkillGuidance`，支持把 Skill 内容加入 Prompt | 复用现有注入格式，必要时增加文档意图判断 |
| `src/main/agent/ipc.ts` | 从用户选择的 `activeSkillPaths` 生成 `activeSkillDocs` | 保留现有手动 Skill 行为，不要求用户选择内置 Skill |
| `src/main/agent/pi-local-files.ts` | 提供受授权目录约束的本地 `read` 工具 | 不为读取内置 Skill 扩大本地文件授权范围 |
| `electron-builder.yml` | 当前已包含 `resources/**/*`，并配置 `asarUnpack: resources/**` | 优先复用现有资源打包规则 |

注意：

1. 当前 `activeSkillDocs` 主要来自用户主动选择的 Skill 路径，尚未实现文档写作意图的自动注入。
2. 当前 `buildActiveSkillGuidance` 已有内容长度限制（`SKILL_CONTENT_MAX_CHARS = 2000`）。内置 Skill 应保持精简，确保完整注入、不被截断；确有必要时再评估调整限制。
3. Pi 原生 Skill 资源加载机制主要向模型提供 Skill 描述和文件位置，再要求模型通过 `read` 工具读取内容。墨巡的 `read` 工具受用户授权目录限制，因此本轮优先由 Main 进程读取随应用打包的内置 Skill 文件，再复用 `activeSkillDocs` 注入 Prompt。**不要为了读取内置 Skill 而放宽本地文件访问权限。**
4. `buildAgentSkillContext` 等现有技能匹配代码若未接入当前主运行链，不要为了本需求顺手重构整个 Skill 系统。

## 3. 实施方案

### 3.1 新增唯一的内置 Skill 文件

新增：

`resources/skills/document-writing/SKILL.md`

文件采用简洁的 Skill Markdown 结构，至少包含：

- `name: document-writing`
- `description`：明确描述适用任务，让系统能够识别文档写作意图。
- 正文：写作流程、可靠性要求、常见文档结构、排版规范和完稿检查。

Skill 内容控制在现有 2000 字符注入上限以内，优先写可执行规则，不堆砌写作理论和大量示例。

### 3.2 文档写作意图自动识别

在现有 Prompt 组装链路中增加轻量判断，不引入新 Agent 或外部分类服务。

**应触发的意图：**

- 创建、撰写、编写、起草、生成文档。
- 整理内容、聊天记录、会议记录并形成正式文档。
- 修改、重写、润色、完善、校对、规范化、排版现有文档。
- 将文档转换为用户要求的正式交付格式。
- 明确提出 SOP、技术方案、项目计划、故障报告、架构说明、README、操作手册、研究报告、论文、会议纪要、规范或指南等文档产物。

英文请求也应识别，例如 write、draft、create、organize、revise、rewrite、polish、format 与 document、report、proposal、SOP、runbook、guide、README、paper 等组合。

**不应触发的情况：**

- 普通技术问答，例如“MongoDB 的 WiredTiger 是什么”。
- 仅询问“如何写好 SOP”或讨论写作方法，没有要求生成或修改文档。
- 普通代码编写、命令解释、终端排障和运维问答。
- 普通短信、聊天消息、简短回复等非正式文档任务，除非用户明确要求按正式文档处理。

对“继续修改”“再完善一下”“按上面的结构整理”等短续接请求，可以结合当前对话中紧邻的文档任务判断；不要因为历史上下文中曾经出现过文档关键词，就让后续所有普通对话都触发。

将意图判断做成可单元测试的纯逻辑函数，优先放在现有 Prompt 相关模块，不新增复杂路由框架。

### 3.3 自动注入 Skill 内容

在 `src/main/agent/pi-host.ts` 的 `runPiAgent` Prompt 组装阶段：

1. 判断当前用户请求是否属于文档写作任务。
2. 命中时，由 Main 进程读取 `resources/skills/document-writing/SKILL.md`。
3. 将读取结果转换为现有 `SkillPromptPart` 结构，追加到本轮 `activeSkillDocs`。
4. 调用现有 `buildPromptText`，让 `buildActiveSkillGuidance` 将内置 Skill 内容注入本轮 Prompt。
5. 如果用户已经手动选择了其他 Skill，保留原有内容并合并注入；不得覆盖、丢弃或重复注入。
6. 未命中文档写作意图时，不加载该 Skill，避免增加普通对话的上下文消耗。

内置 Skill 路径必须通过项目运行时路径解析，兼容开发模式和打包后的 macOS 应用；禁止写死当前开发机的绝对路径。优先检查 `app.getAppPath()` 与现有资源路径工具的适用性。

内置 Skill 文件读取失败时，记录可定位的日志并让正常 Agent 请求继续运行，不得因为 Skill 文件缺失导致整个对话失败。

### 3.4 Skill 固化的写作规范

Skill 正文只需要固化以下规则：

**A. 先组织内容**

- 理解文档目的、读者和交付形式。
- 动笔前形成合理大纲，避免想到哪里写到哪里。
- 章节之间有明确的逻辑关系，重点前置，减少重复。
- 根据文档类型组织结构，不强行套用同一个模板。

**B. 专业、自然地表达**

- 使用准确的专业术语，全文保持术语和命名一致。
- 表达简洁、自然、严谨，避免空话、套话、营销腔和明显的 AI 模板句。
- 不为了消除 AI 痕迹而删掉必要的技术细节、条件、警告或限定。
- 不用冗长总结重复正文已经表达的结论。

**C. 保证事实可靠**

- 不编造数据、版本、命令、参数、输出、案例、引用或来源。
- 区分已确认事实、推断、建议和待确认事项。
- 资料不足时明确标记，不用看似合理的内容填补空白。
- 技术步骤、配置和参数应以已有资料、源码或可靠来源为依据。
- 用户提供的事实和约束必须保留，不能擅自改写成另一种结论。

**D. 自动适配文档结构**

- SOP：目的与范围、前置条件、备份与风险、操作步骤、验证、异常处理和回滚。
- 技术方案：背景与现状、目标与约束、设计方案、实施步骤、风险、测试和验收。
- 故障报告：现象、时间线、证据、原因分析、已确认根因、处理过程、验证和后续措施。
- 项目计划：目标、范围、任务拆分、依赖关系、执行顺序、风险和验收标准。
- 会议/聊天整理：背景、关键结论、决策、待办事项、负责人和待确认问题。
- 研究报告/论文：研究问题、资料来源、方法、分析、结论、局限和参考文献。

以上是结构参考，应按实际内容取舍，不得为了填满目录而制造空章节。

**E. 排版规范**

- Markdown 默认使用清晰的标题层级，避免标题层级跳跃。
- 步骤使用有序列表，并保持编号连续。
- 并列事项使用无序列表；只有需要横向比较多个属性时才使用表格。
- 命令、配置、日志和代码使用代码块，保留原始内容。
- 风险、警告、注意事项使用统一且克制的标记。
- 长文按需提供目录；短文不强制生成目录。
- 统一日期、单位、标点、术语、链接和引用格式。
- 用户提供模板时优先遵循模板，不擅自改变其规定的章节和样式。

**F. 完稿检查**

交付前检查：结构是否完整、逻辑是否连贯、事实是否有依据、术语是否统一、是否存在重复或矛盾、操作步骤是否可执行、目录编号和排版是否正确、引用和链接是否有效。
