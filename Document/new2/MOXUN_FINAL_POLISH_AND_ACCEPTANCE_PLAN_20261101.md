## 1. 本轮目标与原则

本轮不是新增功能版本，也不是重新设计墨巡，而是产品收尾：

1. 修复截图和源码审查中确认的交互问题，尤其是多模态能力提示、错误展示和运行状态信息。
2. 收敛重复 UI 与过度耦合的代码，降低后续维护成本。
3. 彻底核验 Agent 终端执行边界，清理已经失去用途的旧执行代码，但不能破坏人工终端操作。
4. 对长会话、iTerm 生命周期、异常退出等尚未充分覆盖的场景补充测试。
5. 保留现有墨巡品牌、深色水墨主题、三栏工作方式和已完成的交互，不推翻当前 UI。

### 必须遵守的原则

- **不新增大型业务模块**，不借收尾之名扩展产品功能。
- **不重做整体 UI**，以局部修正、组件职责收敛为主。
- 不为减少行数而机械拆分组件；只有职责独立、状态边界清楚时才拆分。
- 不引入未经测量证明必要的性能依赖。
- 不提交 Git、不推送、不打包、不发布；除非用户另行明确要求。
- 修改前先检查当前工作区和未提交改动，不覆盖用户已有修改。
- 任何安全边界调整都必须有 Main 进程层面的测试，不得只依赖 Renderer 隐藏按钮或提示词约束。

## 3. P0：多模态附件与模型能力预检

### 当前发现

涉及：

- `src/renderer/src/components/ChatWorkspace.tsx`
- `src/shared/model-capabilities.ts`
- `src/main/agent/multimodal.ts`
- `src/renderer/src/lib/agent-config.ts`
- `src/renderer/src/components/SettingsSheet.tsx`

当前输入区会根据 `activeModel?.capabilities?.imageInput` 显示 Vision + text 或 Text only，但附件说明仍固定显示 PNG / JPEG / WebP / PDF / Text。用户可以先添加图片并提交，随后 Main 端的 `prepareModelAttachments()` 才以 `imageInput` 拒绝请求。

Main 端检查必须保留，但 Renderer 应提前给出清晰反馈。

### 改造要求

1. **发送前预检**
   - 用户选择图片后，立即根据当前 Provider + Model 的能力判断是否可发送。
   - 不支持视觉输入时，不应让用户走到请求提交后才看到错误。
   - 给出明确操作：切换到视觉模型，或移除图片后继续发送。
   - 如果用户切换模型，应重新校验当前附件；不能沿用旧模型的校验结果。
   - 若模型配置缺失能力字段或状态未知，按不支持视觉处理，不得猜测支持。

2. **模型选择器**
   - 在模型选项中显示简洁能力标识，例如“视觉”“纯文本”。
   - 能力依据 Provider 声明的模型配置，不根据模型名称、品牌或字符串猜测。
   - 同名模型在不同 Provider 下可能有不同能力，必须按实际 Provider + Model 组合判断。
   - 设置页说明 `imageInput` 的含义及配置方法。

3. **附件提示动态化**
   - 当前模型为纯文本时，不能把 PNG / JPEG / WebP 描述成当前可直接发送的能力。
   - 明确区分图片视觉输入、PDF 文本提取、普通文本附件。
   - PDF 可提取文本时，不应因为模型没有视觉能力就一概禁用 PDF；无可提取文本的 PDF 才提示需要视觉模型或页面图片。
   - 展示当前附件限制时，统一以 Main 端实际限制为准，避免前后端文案不一致。

4. **安全校验保留**
   - Main 端继续校验文件路径授权、文件类型、MIME 与真实文件头、文件大小、总大小、图片尺寸、PDF 页数和文本脱敏。
   - 图片发送前的隐私确认必须保留；图片像素无法自动脱敏这一事实应继续明确告知。
   - Renderer 预检只是用户体验层，不能替代 Main 端权威校验。

### 验收

- 纯文本模型添加 PNG/JPEG/WebP：发送前提示，不产生模型请求。
- 视觉模型添加受支持图片：正常进入现有 Main 校验和隐私确认流程。
- 添加图片后切换成纯文本模型：立即更新状态并阻止误发。
- 添加图片后切换为视觉模型：重新校验后允许继续。
- Provider A 的模型能力不能错误套用到 Provider B 的同名模型。
- PDF 可提取文本时，纯文本模型仍可分析提取出的文本。
- Main 端绕过 Renderer 直接调用时，仍然拒绝不支持的图片请求。

## 4. P1：统一错误呈现，消除重复信息

### 当前发现

涉及：

- `src/renderer/src/hooks/useAgentRuns.ts`
- `src/renderer/src/components/AgentRunTimeline.tsx`
- `src/renderer/src/components/AgentLogContent.tsx`
- `src/renderer/src/lib/agent-event-formatters.ts`

当前 `useAgentRuns` 在收到 `error` 事件时，会更新 run 的 error 字段，同时向 steps 追加 status 步骤；`AgentRunTimeline` 又会单独渲染 `document.errorMarkdown`。这会造成同一错误在状态步骤和错误结果区重复出现，截图中可见类似现象。

### 改造要求

1. 为一次 Agent Run 统一错误呈现模型，避免同一错误同时以普通状态步骤和最终错误卡片重复展示。
2. 错误事件可以保留结构化字段：错误类别、Provider、可重试性、用户可读说明、原始诊断文本。
3. 最终错误卡片作为唯一主要错误入口；运行时间和必要的诊断信息放在同一卡片或折叠详情内。
4. 区分 quota、transient、模型能力不匹配、附件校验失败、连接失败和未知错误。
5. 不要简单删除所有 status 步骤：正常分析、工具状态、审批状态仍应保留；只合并同一个错误事件产生的重复呈现。
6. 对 Provider 返回的任意原始英文错误，不要尝试用脆弱的字符串替换伪造翻译。优先将已知错误映射为本地化文案，原始错误放入“技术详情”。
7. 错误卡片操作按场景收敛：
   - transient：提供重试（前提是重试语义安全且不会重复产生副作用）。
   - quota：提供模型设置入口和额度说明。
   - vision mismatch：提供切换视觉模型入口。
   - attachment validation：指出具体文件及原因，允许移除或替换附件。
   - 通用错误：复制错误详情、查看运行记录。
   - 错误结果不应默认提供“保存 SOP”、点赞/点踩等与成功结果更相关的操作。
8. 完整 Trace / JSON 导出可以保留，但放入更多操作或诊断入口，减少普通错误卡片的图标密度。

### 验收

- 同一错误事件在时间线中只出现一次主要错误内容。
- quota、transient、未知错误分别显示正确状态和可用操作。
- 错误标题、已知说明和操作提示跟随当前语言。
- 原始 Provider 错误仍可在技术详情中查看和复制。
- 重试不会重复提交已经产生副作用的操作；无法保证安全时不提供自动重试。

## 7. P1：Agent 终端执行遗留路径清理与安全边界回归

### 背景与约束

本项目已经明确采用 Agent 分析与人工执行分离的安全模型。本轮必须保持以下不变量：

- Agent **没有终端命令执行能力**，不是仅隐藏执行按钮，也不是增加一个可切换的安全模式。
- Agent 不得向 PTY / iTerm 写入命令，不得代替用户按回车，不得通过 bash、MCP、Subagent 或其他工具绕过限制。
- 用户可以正常使用自己的本地终端和 SSH 终端。
- Agent 可以分析经授权的终端观察结果、提出建议；实际命令由用户自行审阅和执行。
- 本地文件可以由应用工作流修改，但必须经过用户明确批准；不得绕过现有文件审批策略。
- Main 进程是安全边界的权威执行位置，Renderer、提示词和 UI 只能作为辅助层。

### 当前审查线索

重点检查：

- `src/main/agent/pi-terminal-bash.ts`（仍保留较多旧执行上下文和相关逻辑）
- `src/main/agent/pi-host.ts`
- `src/main/agent/pi-subagent.ts`
- `src/main/terminal/`
- `src/main/security/`
- `scripts/check-security-boundaries.cjs`

当前代码中仍可看到 PTY bash execution context 的设置、清理或克隆调用。不能仅凭文件名或代码行数判断这些代码可删除，必须先画出调用关系。

### 执行步骤

1. 盘点 Agent 主会话、Subagent、MCP、工具注册、IPC、PTY 和终端输入的完整调用链。
2. 将“用户人工输入/执行”与“Agent 发起的执行”分开标记，确认所有入口都有 Main 层身份和权限校验。
3. 对旧执行模块逐项分类：
   - Agent 命令执行能力；
   - 人工终端输入能力；
   - 终端会话生命周期和元数据；
   - 观察授权与证据读取；
   - 审批及审计能力。
4. 只删除已确认不再使用、且属于 Agent 直接执行路径的逻辑。
5. 将仍被人工终端、PTY 生命周期或观察链路使用的通用代码保留或迁移，不得一并删除。
6. 删除旧代码后，清理无用类型、导入、配置项、提示词和过期测试。
7. 保留 Main 层默认拒绝策略。即使 Renderer 被绕过或伪造 IPC 请求，也不能让 Agent 获得 PTY 写入、命令执行或中断能力。
8. 本地文件修改审批保持原样；补充测试证明 Agent 不能通过其他工具路径绕过批准。

### 必须具备的安全回归

- 主 Agent 工具列表不包含可执行 Shell / bash 工具。
- Subagent 工具列表不包含可执行 Shell / bash 工具。
- 伪造或直接调用相关 IPC 时，Main 层拒绝 Agent 来源的 PTY 写入。
- Agent 无法调用终端输入、执行、发送回车或中断用户命令的接口。
- MCP 工具不能间接获得终端执行能力。
- 人工在本地终端和 SSH 终端中输入、执行命令仍正常。
- Agent 仍能在用户授权范围内读取终端观察证据。
- 观察授权撤销、终端切换、PTY 重开后，旧证据和旧建议不能越权复用。
- 本地文件写入仍要求用户批准；拒绝批准后不能产生文件变更。

**禁止为了让测试通过而放宽 Main 层拒绝策略。** 如果旧代码仍有实际用途，应先重构隔离，再决定删除范围；不要进行一次性大删改。

## 9. P2：长会话性能基准与必要优化

当前消息列表使用常规列表渲染。先测量，再决定是否虚拟化。

### 基准场景

- 100 条消息；
- 500 条消息；
- 1000 条消息；
- 包含大量代码块、长日志、表格和 Agent Timeline 的混合会话；
- 多次切换历史会话；
- 连续流式输出并同时滚动。

### 记录指标

- 首次打开会话耗时；
- 历史消息加载耗时；
- 滚动时的明显卡顿和掉帧；
- DOM 节点数量；
- Renderer 内存增长；
- 流式输出期间主线程响应；
- 会话切换后的残留订阅和内存释放情况。

### 优化策略

1. 先确认是否由 Markdown 渲染、Timeline 复杂度、重复计算或过多 DOM 导致。
2. 优先做 memoization、减少不必要的状态更新、按需解析历史消息和限制单条超长内容。
3. 只有实测证明普通列表存在明显瓶颈，才引入虚拟列表。
4. 虚拟化必须兼容自动跟随、回到最新、向上查看历史、消息锚点、代码块展开和复制操作。
5. 不得以性能优化为由降低日志保留、审计记录或用户可访问的历史内容。

### 验收

- 输出优化前后相同数据集的测量结果。
- 不能只报告主观“感觉更流畅”。
- 自动滚动、历史加载、复制、展开和会话切换均通过回归。
- 若没有显著瓶颈，记录测量结论并不引入虚拟化依赖。

## 10. P1：iTerm / PTY 生命周期与异常恢复补验

上一轮实施报告已经记录若干真实 iTerm、共享 PTY、观察授权和重开场景的通过结果。本轮不要重复宣称这些历史测试是新测试，也不要破坏已通过的路径。

重点补足此前仍未充分验收的边界：

1. 应用正常退出时，本轮创建的 PTY、Socket、观察订阅和监听器是否按预期释放。
2. Main 进程异常退出或被强制终止时，是否留下孤儿 PTY、Socket 或僵尸子进程。
3. 原生授权窗口打开期间退出应用，授权结果是否可能回写已销毁窗口或恢复已撤销权限。
4. iTerm 窗口关闭、用户关闭共享画面、重开同一 PTY、新 UUID 等路径是否保持身份隔离。
5. 用户原有 iTerm 窗口和会话必须保留；测试只能清理本轮创建的临时会话。
6. SSH 密码、私钥、Agent 转发等不同认证路径应区分测试；未测的认证方式不能写成全部通过。
7. 所有异常恢复都必须保证 Agent 不能借恢复逻辑获得终端写入权限。

### 验收

- 正常退出和异常退出分别有测试记录。
- 没有残留本轮创建的 PTY、Socket 或子进程。
- 用户原有终端会话不受影响。
- 观察授权在退出、撤销、重开和身份变化后均不会意外恢复。
- 测试失败保留原因和日志，不得通过跳过测试伪造通过。
