## 1. 目标与范围

将当前“会话压缩 + 基础知识记忆”增强为一套可靠的会话上下文管理能力，重点解决：

1. 长会话压缩后，任务目标、关键事实、用户决策、命令和验证结果容易丢失。
2. 压缩后的信息缺少可追溯来源，无法准确找回原始对话和工具证据。
3. 现有长期记忆偏向人工审核的知识条目，缺少“发生过的事实”与“从多次事实归纳出的经验”的区分。
4. 记忆召回主要依赖关键词包含关系，中文、路径、IP、端口、版本号和错误信息的检索质量不足。
5. 会话恢复时缺少明确的工作检查点，未完成事项和下一步容易断档。
6. 自动整理、记忆召回和上下文压缩之间缺少统一的预算、状态和质量验证。

### 本次实施边界

- 只改进会话上下文、压缩、历史召回、长期记忆及其必要的数据持久化。
- 优先复用现有 SQLite、历史记录、Memory Center、自动学习和会话压缩入口。
- 保留当前产品行为和已有权限边界；不借本计划扩展其他业务能力。
- 不引入新的数据库服务，不默认引入 Embedding 服务或大型 Agent 框架。
- 不把第三方项目作为运行时依赖；仅借鉴成熟设计并在现有代码中实现必要能力。
- 不大规模重做 UI；只增加完成记忆审核、来源查看和压缩状态所必需的轻量呈现。
- 不删除或覆盖原始会话日志。摘要、检查点和记忆均是索引/派生数据，原始记录仍是事实来源。

### 已确认的具体限制

- 当前记忆类别为 `environment / architecture / operation / troubleshooting / preference`，状态为 `candidate / approved / archived`。
- 记忆条目上限为 2000 条；完全相同的作用域、类别、标题和内容通过 fingerprint 去重。
- 当前 `recall()` 只返回已批准条目，按简单 Token 包含次数排序，最多返回 6 条。
- 中文检索通过相邻双字切分；英文、数字、路径和符号串使用简单词元化，尚无专门的历史消息全文检索。
- 历史整理读取最多 2000 条消息、12 万字符；超限会拒绝并提示分段整理，不会误标记已学习。
- 自动学习默认关闭；远程历史整理仍需要明确授权，不能移除现有授权检查。
- 当前压缩入口调用托管会话的压缩能力并报告 Token 变化；原始 Agent Logs 由独立历史存储维护。实施时必须验证两者的一致性，不得假设压缩会自动产生可靠的持久化检查点。
- 现有记忆上下文已经明确标记为历史资料而非指令；后续实现必须继续保持这一语义。

## 3. 目标体验

### 3.1 长会话压缩后

墨巡应继续掌握：

- 用户最初的目标，以及后来明确修改过的目标。
- 用户明确提出的限制、偏好和已作出的决定。
- 已确认事实及其时间、作用域和来源。
- 已提出、已尝试、失败、成功、已验证、未验证的操作状态。
- 关键命令、参数、错误信息、IP、端口、路径、版本、服务名和资源名。
- 当前进度、未完成事项、阻塞原因和下一步。
- 哪些结论只是推测，哪些已经被用户或可靠证据确认。

不能把“建议执行”写成“已经执行”，不能把“命令返回成功”写成“业务验证成功”，也不能把历史环境值自动当作当前环境值。

### 3.2 需要历史细节时

Agent 可以先搜索历史记录，获得带来源的短摘录；只有在确实需要时才继续读取相邻消息或更完整的证据。默认上下文不应装入全部历史。

### 3.3 长期记忆逐步形成

- Observation（观察）：某次会话中实际发生、被明确陈述或被证据支持的事实。
- Reflection（反思）：从多条已审核观察中归纳出的稳定规律、操作经验或架构知识。
- Existing Knowledge（既有知识）：兼容当前已保存的知识条目，不强行改变其历史含义。

观察和反思均需要来源、作用域、置信度和审核状态。模型生成不等于事实成立；新提取内容默认进入候选状态，继续由用户审核。

## 4. 总体设计

采用“原始记录 + 结构化检查点 + 可检索证据 + 审核记忆”的组合：

1. **原始历史层**：继续以现有 Conversation / Agent Logs / Runs 为事实源，不重复复制整段日志。
2. **压缩检查点层**：每次成功压缩前后生成结构化检查点，保存工作状态和原始消息引用。
3. **历史检索层**：对原始消息和检查点建立可维护的索引，返回精确来源及有限摘录。
4. **长期记忆层**：在现有 Memory Service 上增加 Observation / Reflection 及证据关联。
5. **上下文组装层**：按任务相关性和 Token 预算选择近期消息、最新检查点和少量相关已批准记忆。
6. **质量验证层**：检查关键事实是否仍可从检查点或原始证据恢复；验证失败不删除原始数据，不把失败状态伪装成成功。

设计借鉴方向：
- pi-vcc：确定性提取、结构化压缩和原始历史 Recall。
- pi-smart-compact：压缩前后检查、证据归档和工作检查点。
- pi-observational-memory：观察事实与归纳反思分层。
这些项目只作为设计参考，不要求直接安装、引入依赖或复制其完整实现。

## 5. 会话压缩增强

### 5.1 压缩前：生成 Preservation Manifest

在现有压缩入口调用底层压缩前，从当前会话上下文和已持久化日志中生成一份确定性的“关键信息保护清单”。不要只依赖模型自由总结。

建议结构：

```ts
interface ContextPreservationManifest {
  conversationId: string
  sourceRevision: string
  createdAt: string
  userGoal: string[]
  constraints: string[]
  decisions: Array<{ text: string; sourceLogIds: number[] }>
  confirmedFacts: Array<{
    subject?: string
    key?: string
    value: string
    scope?: string
    observedAt?: string
    sourceLogIds: number[]
  }>
  operations: Array<{
    status: 'proposed' | 'attempted' | 'failed' | 'succeeded' | 'verified' | 'unknown'
    command?: string
    result?: string
    sourceLogIds: number[]
  }>
  errors: Array<{ text: string; sourceLogIds: number[] }>
  pending: string[]
  blockers: string[]
  nextSteps: string[]
  importantIdentifiers: string[]
}
```

字段可按真实消息结构调整，不要求为了满足示例而过度复杂化。所有数组和字符串必须有长度上限；来源 ID 必须能在原始历史中查到。

确定性提取规则：

- 优先从有明确角色、时间和消息 ID 的原始消息中提取，不从已经压缩过的摘要反推事实。
- 对代码块、命令、路径、IP、端口、版本号、服务名、资源名、错误码等精确保留原文片段；禁止对这些值做语义改写。
- 识别“用户明确确认”“模型建议”“用户准备执行”“已执行”“执行失败”“结果已验证”等不同语义，不能合并成同一状态。
- 保留否定、条件和范围，例如“不要重启”“仅 web2”“只检查不修改”。
- 同一事实有多个版本时保留时间和来源，不以最新文本简单覆盖旧记录。
- 对不确定内容明确标注 unknown / unverified，不补全模型猜测。

### 5.2 生成结构化工作检查点

在每次手动压缩前生成检查点，内容至少包括：

- 当前目标和任务范围。
- 用户约束及明确决策。
- 已确认事实与重要标识符。
- 已完成事项、失败事项和待验证事项。
- 当前进度、阻塞原因和下一步。
- 对应原始消息 ID、必要的短摘录和源修订号。
- 本次压缩前 Token 使用量、模型上下文窗口和创建时间。

检查点保存结构化 JSON 与简短 Markdown 摘要。不要把整段 Agent Logs 再复制一份到检查点表。

### 5.3 执行压缩

- 保留现有手动压缩入口、忙碌状态判断、会话互斥和取消/错误处理。
- 为现有压缩指令增加结构化摘要要求，优先保留目标、约束、决定、事实、操作状态、错误和待办。
- 压缩算法优先采用“确定性保护清单 + 现有压缩能力”，避免额外调用模型重复总结同一批内容。
- 近期对话保留策略应按上下文预算决定，不固定粗暴地保留最后 N 条；至少保证最近用户目标、最近关键决策和未完成操作不被清理。
- 检查当前 SDK 是否已经提供自动压缩机制。若已有可靠机制，应扩展其指令/前后处理，不再叠加第二套触发器。
- 若当前没有可靠的自动压缩触发，则增加受控的预警和自动压缩：以实际 context usage 为依据，设置可配置阈值和滞回区间；默认在约 80% 提示、约 85% 进入自动压缩评估，最终阈值必须结合输出 Token 预留和模型窗口验证。压缩中不得重复触发。
- 手动压缩仍可用；自动压缩失败不能阻止用户继续查看历史或手动处理。

### 5.4 压缩后验证

压缩完成后：

1. 获取压缩后的上下文/摘要和最新会话修订号。
2. 检查检查点中的关键目标、约束、决定、关键标识符和操作状态是否仍可恢复。
3. 检查每个 sourceLogId 是否存在；已删除或修订的消息不能继续作为有效来源。
4. 对关键命令、路径、IP、端口、版本和错误码进行精确字符串保护检查；不能仅靠语义相似判断。
5. 将验证结果记录为 `passed / partial / failed`，并列出缺失项。
6. 若底层压缩摘要遗漏关键信息，优先在后续上下文组装时补入结构化检查点，不要盲目连续重复压缩。
7. 失败时保留原始历史和检查点，显示可理解的失败状态；不得返回“压缩成功”而没有质量状态。

验证不要求所有历史细节都塞进模型上下文。验收重点是：关键事实有检查点或来源引用，Agent 需要时能准确召回。

### 5.5 重复压缩和异常恢复

- 同一会话同一 sourceRevision 的检查点生成应幂等。
- 已经验证通过且源修订号未变化时，不重复生成同一检查点。
- 压缩中途应用退出、模型超时或取消时，保留未完成记录为 interrupted；下次启动可安全重试。
- 不允许并发压缩同一会话；继续使用现有会话互斥机制。
- 记录压缩前后 Token、耗时、状态和失败原因，不记录未脱敏原始敏感内容。

## 6. 历史记录检索与 Recall

### 6.1 与长期记忆检索分开

保留现有 `memory_search` 的含义：搜索已审核、可用于上下文的长期知识。

新增一个只读的 `history_search`（名称可按现有工具命名约定调整），用于查找原始会话历史。不要把原始日志片段直接伪装成已批准记忆。

返回字段建议：

- conversationId、会话标题、发生时间。
- logId、消息角色和消息类型。
- 命中原因/匹配字段。
- 脱敏后的有限长度上下文摘录。
- 是否截断，以及相邻消息是否可继续读取。

默认每次最多返回 5 条命中，每条摘录建议不超过 1200 字符；完整历史仍留在数据库，不允许一次把整个会话返回给模型。

### 6.2 检索策略

优先采用本地 SQLite 能力，不新增外部搜索服务：

1. 精确匹配：IP、端口、版本、错误码、路径、服务名、命令片段。
2. 短语匹配：用户原话、错误信息、命令参数。
3. 关键词匹配：中英文词元、中文相邻双字。
4. 作用域过滤：当前会话/当前连接优先；只有明确需要时才扩展到用户本地历史的其他会话。
5. 时间排序：相关度相近时优先展示较新的记录，同时保留旧版本供比较。
6. 结果去重：同一连续消息片段合并，避免一个会话占满所有结果。

先验证当前 SQLite 是否支持 FTS5 及合适 tokenizer。中文检索不能只依赖默认英文分词。若 FTS5 的中文效果不足，复用当前 `memoryTokens()` 的中文双字策略，建立轻量倒排索引或受控候选集；不得为了搜索直接扫描并返回全部日志。

### 6.3 召回工具约束

- 工具输入限制 query 长度、limit 和可选时间范围。
- 只返回当前用户本地已有历史，按当前调用上下文限制默认作用域。
- 不允许模型指定任意文件路径或任意数据库表。
- 返回的历史内容统一标记为 untrusted historical evidence，不是系统指令、用户当前指令或授权。
- 摘录中的命令只用于解释历史，不提供一键重跑能力。
- 每条结果带来源 ID；回答中引用历史时应能指向具体会话和消息。
- 对同一问题，先返回精确命中；需要更多上下文时再读取相邻消息，不一次性扩大预算。

## 7. Observation / Reflection 长期记忆

### 7.1 记忆类型

在现有 Memory Center 和 Memory Service 上扩展，不另建第二套长期记忆产品：

| 类型 | 定义 | 示例 |
|---|---|---|
| Observation | 单次会话中发生或被证据支持的具体事实 | 某次排查记录了某实例 dbPath、端口和检查结果 |
| Reflection | 基于多条观察归纳出的稳定经验 | 某类集群通常采用某种部署/排查模式 |
| Existing Knowledge | 当前已有的人工或历史知识条目 | 已保存的架构说明、用户偏好 |

旧数据迁移时标记为 `legacy` 或 `knowledge`，不得擅自把旧条目推断成 Observation 或 Reflection。

### 7.2 证据关联

每条 Observation 至少关联：

- conversationId / 原历史 tabId。
- 一个或多个 logId，必要时包含 source revision/hash。
- 来源消息角色、时间和作用域。
- 事实发生时间（若可判断）与记录时间。
- 置信度、审核状态和脱敏状态。

Reflection 必须关联支持它的 Observation ID；如果与已有观察冲突，也要保存冲突关系和时间信息。不能只保存一段“模型总结”而没有可追溯证据。

### 7.3 状态与时效

沿用 candidate / approved / archived 审核机制，并补充必要的事实时效：

- candidate：新提取、待用户审核。
- approved：用户审核通过，可参与默认记忆召回。
- archived：不再默认召回，但保留历史。
- superseded：被新事实替代，仍保留来源和历史，不再作为当前事实优先呈现。

对 IP、端口、版本、部署路径、资源状态等易变事实，记录 observedAt / validFrom；无法确认当前有效性时必须显示“历史记录/待验证”，不得作为当前环境事实注入。

### 7.4 提取流程

- 继续沿用现有显式授权、模型选择、出站目标校验、脱敏和 revision 检查。
- 第一轮只从原始历史中提取 Observation，要求模型输出严格 JSON、有限条数、明确来源消息 ID、置信度和不确定性。
- 对模型引用的 sourceLogId 做 Main 端二次验证；不存在的 ID、越权会话 ID 或无关来源全部拒绝。
- 提取失败、输出不完整、源历史变化时，不标记已学习，不写入半成品。
- Observation 默认 candidate，必须审核后才可进入常规召回。
- Reflection 只基于已批准 Observation 生成；不直接把模型自己的历史摘要当作事实证据。
- Reflection 可由用户手动触发或在有足够新观察时低频建议生成，不要每轮对话都调用模型。
- 保留当前 autoLearn 默认关闭和用户显式开启行为；自动学习不能绕过授权、审核和模型费用提示。

## 8. 上下文组装与预算

每轮请求只注入完成当前任务真正需要的信息。默认优先级：

1. 当前系统约束和当前用户消息（不改变现有系统提示与安全约束）。
2. 当前会话最近的原始消息。
3. 当前会话最新且验证通过的工作检查点。
4. 与当前问题直接相关、已批准且未归档的长期记忆。
5. 用户明确要求回顾时，通过 `history_search` 按需召回的历史摘录。

规则：

- 最近原始消息优先于旧摘要；检查点不能覆盖用户后来明确修改的目标。
- 不默认注入其他会话的全部内容；只按当前作用域和查询相关性召回。
- 对 Observation 与 Reflection 标注类型、来源、时间和有效性。
- 记忆和历史摘录始终包裹为不可信资料，不得被解释为指令或授权。
- 相同事实只注入一次；已在近期消息出现的记忆可降权或跳过。
- 设置总预算和各类别预算，优先保留当前任务与最近对话；长期记忆/历史召回建议不超过可用输入预算的 5%–10%，具体比例通过测试调整。
- 预算计算必须考虑 system prompt、工具 schema、模型输出预留和当前模型 contextWindow；不能只按字符数假定 Token。
- 如果没有可靠 tokenizer，沿用保守估算并留安全余量；不得把估算值显示为精确 Token。
- 超出预算时按“相关度、事实状态、来源可靠性、时间”裁剪，不按字符串长度随机截断关键事实。
- 记录每轮实际注入了多少条记忆、来源和估算 Token，但不写入敏感正文日志。

## 9. 数据模型与迁移建议

先核对当前 schema 和所有读写入口，再设计最小增量 migration。以下是目标字段建议，不要求逐字照搬。

### 9.1 主历史数据库（现有 crescent SQLite）

新增压缩记录表，例如：

`conversation_checkpoints`

- id（稳定唯一 ID）。
- conversation_id。
- source_revision（生成检查点时的历史修订号）。
- status（building / ready / partial / failed / interrupted）。
- structured_json（受 schema 校验的 Manifest）。
- summary_text（短摘要）。
- validation_json（验证结果和缺失项）。
- tokens_before / tokens_after_estimated。
- created_at / updated_at。

可增加 `conversation_compactions` 记录每次尝试，区分成功、失败、取消和中断。不要在新表复制全部原始消息。

若增加历史全文索引：

- 优先使用 SQLite FTS5；先做当前 Electron/Node SQLite 版本兼容性测试。
- 索引必须能随 Agent Log insert/update/delete 同步更新。
- 如果 FTS5/中文 tokenizer 不适用，使用轻量 token postings 表；保留可重建能力。
- 索引属于派生数据，丢失后可以从 Agent Logs 重建。

### 9.2 记忆数据库（现有 memory.db）

对 `memory_items` 做向后兼容的增量扩展：

- `kind`: legacy / knowledge / observation / reflection。
- `observed_at`、`valid_from`、`valid_to`：事实时间和有效期。
- `supersedes_id`：可选的被替代条目 ID。
- `source_revision`：提取时的源历史修订号。

新增 `memory_evidence` 关联表：

- memory_id。
- conversation_id / source_tab_id。
- source_log_id。
- evidence_role（source / supports / contradicts）。
- source_hash（可选，用于发现源消息变化）。
- created_at。

如果当前 schema 已有等价字段或关系表，优先复用，不重复建表。关系必须可追溯且有索引。

### 9.3 Migration 要求

- 所有 migration 使用现有数据库初始化/迁移入口，带明确版本号，幂等、事务化。
- 旧数据只增加默认值，不删除、不重写内容、不改变已有审核状态。
- 新表建立索引和外键约束；跨两个 SQLite 数据库的操作不得假设可以原子提交。
- 启动迁移失败时明确报错并保留旧数据，不进入“部分迁移但继续写入”的状态。
- 迁移前提供可恢复备份/测试副本策略；至少在本地测试中覆盖旧 schema → 新 schema。
- 索引可以重建；检查点和证据关联不可依赖内存 Map 作为唯一存储。
- 版本升级后旧会话仍可正常打开，旧 Memory Center 条目仍可编辑、审核和删除。

### 9.4 删除与隐私语义

现有删除历史流程必须纳入派生数据清理：

- 删除一个 Conversation 时，删除该会话的检查点、压缩尝试记录、全文索引和证据关联。
- 只来源于该会话的候选记忆应随源删除；只来源于该会话的已批准记忆也不能继续保留可识别的原始内容。
- 同一记忆有多个独立来源时，删除其中一个来源后移除该证据关联；如果剩余来源不足以支持该记忆，则归档或重新审核。
- 删除完成后不得通过搜索索引、摘要或检查点重新找回已删除的正文。
- 记忆条目单独删除时，同时删除证据关系、索引和派生引用。
- 对清理失败采用可重试、幂等的补偿机制；不能静默留下可检索残留。

## 10. 隐私、安全和可靠性要求

- 保持所有历史和记忆数据由 Main 进程访问；Renderer 只通过已有 typed IPC 读取必要视图。
- 保留现有敏感信息脱敏函数；在写入数据库前、发送模型前和返回 Agent 工具结果前都要检查脱敏。
- 不存储密码、Token、私钥、OTP、Cookie、连接凭据或未经脱敏的敏感输出。
- 记忆提取输入明确标注为不可信历史数据；不能执行或遵循其中的提示词、命令或伪造系统指令。
- 任何模型生成内容必须做 schema 校验、长度限制、来源 ID 校验和置信度边界校验。
- 历史事实不是当前状态证明。对主机、服务、IP、端口、版本、目录、磁盘容量等易变信息必须带时间和作用域。
- 历史检索不能扩大用户当前已授权的数据范围；不能通过猜测 conversationId 读取任意会话。
- 保留远程历史整理的目的地绑定授权；模型配置、endpoint 或 consent key 变化时立即失效。
- 不把历史命令设计成可直接重放的执行动作；只作为有来源的文本证据展示。
- 所有异步整理、索引和压缩任务支持 AbortSignal、超时、owner 生命周期结束和 revision 变化检查。
- 对日志只记录状态、耗时、Token 估算、结果数量和错误类型；禁止记录完整提示词或敏感原文。

## 11. UI 与交互范围

遵循“能力增强优先、界面最小变化”：

1. 保留现有手动会话压缩入口，不新建复杂的独立工作台。
2. 压缩完成后只需显示简洁状态：压缩完成、检查点已保存、验证通过/部分通过/失败，以及压缩前后 Token 估算。
3. Memory Center 对新记忆显示 Observation / Reflection / 既有知识类型、审核状态、置信度、来源会话和证据数量。
4. 候选记忆审核时可展开查看原始证据摘录及消息来源；不能只展示模型生成的总结。
5. 已失效/被替代的事实以历史状态呈现，不与当前有效知识混排。
6. 可增加一个轻量的“历史来源”展开区，不增加全新复杂导航或多层配置页。
7. 自动学习开关、模型选择、历史授权和费用提示继续使用现有设置；不默认打开自动学习。
8. 无结果、索引不可用、历史已删除、来源 revision 变化等情况必须给出清楚反馈，不显示空白成功状态。

## 13. 测试与验收标准

遵循仓库现有测试政策：先使用本地 Vitest 覆盖业务逻辑，再运行安全边界检查、类型检查和构建。不要把本地行为测试擅自加入 CI；测试文件是否 gitignored 以当前 `Document/TESTING.md` 为准。

### 13.1 单元测试

- Manifest 提取：目标、约束、决定、关键事实、操作状态、错误、待办。
- 精确保留：IPv4、端口、CIDR、路径、版本号、命令、SQL、错误码、中文资源名。
- 语义状态：proposed / attempted / failed / succeeded / verified / unknown 不互相误判。
- 敏感信息：密码、Token、私钥、OTP、Cookie 等不会进入 Manifest、摘要、索引或模型上下文。
- Revision：历史新增、编辑、删除都会使旧检查点/旧提取结果失效或标记过期。
- 幂等：同一 sourceRevision 重复压缩不重复生成无意义记录。
- 并发：同一会话压缩与学习任务互斥；取消和超时能正确释放状态。
- 验证器：精确字段缺失、来源不存在、摘要不完整时给出 partial/failed，而非 passed。
- 记忆：Observation/Reflection 关系、审核状态、时效、冲突、supersedes 和多来源。
- 检索：中文、英文、混合数字、路径、IP、端口、错误码、命令片段和时间过滤。
- 删除：历史删除后，检查点、索引、证据关系和仅来源于该历史的记忆均不可召回。

### 13.2 集成测试

使用完全合成、脱敏的本地对话 fixture，不连接真实业务环境、不调用付费模型：

1. 创建一段包含多轮需求变更、用户约束、命令建议、执行失败、后续成功、待验证项的长对话。
2. 执行第一次压缩，检查 Manifest、检查点、压缩记录和原始日志。
3. 继续对话并再次压缩，检查旧决定与新决定的关系、历史证据可召回性。
4. 模拟模型超时、压缩中止、应用重启和历史 revision 变化。
5. 检索指定 IP、端口、路径、版本、命令和错误，确认结果带准确的会话/消息来源。
6. 通过 Memory Center 审核 Observation，再生成 Reflection，验证 Reflection 必须引用已批准 Observation。
7. 删除源会话，验证派生数据清理及多来源记忆的剩余证据处理。
8. 使用旧版数据库副本执行迁移，验证旧 Memory 条目、历史会话、审核状态和关联不丢失。

### 13.3 端到端验收

- 连续压缩至少 3 次，仍能准确回答 fixture 中所有标记为 critical 的关键事实；精确字段必须 100% 可从检查点或原始来源恢复。
- 对 20 组预设历史查询，Top 5 结果必须包含对应正确来源；不允许只返回相似但不同主机/端口/版本的记录。
- 任何模型建议、未执行命令、失败命令不得被记为已成功。
- 任何过期事实不得不带时间地呈现为当前事实。
- 每条 Observation / Reflection 均可追溯来源；没有来源的条目不能进入 approved 状态。
- 自动学习关闭时不发生后台模型整理；开启后仍受现有授权、冷却和 revision 约束。
- 压缩验证失败时，原始历史可用、会话仍可继续、用户能看到失败原因。
- 删除历史后，相关内容不能从搜索索引、检查点或记忆引用中重新出现。
- 记忆上下文注入有明确 Token 上限；没有相关记忆时不产生空壳提示词。
- 不新增持续运行服务，不增加启动时全量扫描全部历史的阻塞。

### 13.4 性能与成本记录

实施前后对同一组 fixture 记录：

- Manifest/检查点生成耗时。
- 历史搜索 P50/P95 耗时。
- 索引体积和数据库增长量。
- 每次记忆整理输入/输出 Token 与调用次数。
- 上下文组装注入的记忆条数和估算 Token。

不以某个开源项目公布的压缩率作为墨巡验收目标。先建立本项目真实基线，再决定后续阈值；不得为了追求压缩率牺牲关键事实。

## 15. 风险与处理

| 风险 | 处理要求 |
|---|---|
| 压缩摘要遗漏关键事实 | Manifest 与原始证据独立保存；验证失败标记 partial/failed |
| LLM 将建议误写成已执行 | 以消息角色和证据状态为准；不确定时标记 unknown |
| 旧事实覆盖新事实 | 保留时间、来源和 supersedes 关系 |
| 中文全文检索不准确 | FTS5 先验证；必要时使用中文双字倒排索引 |
| 历史删除后仍可召回 | 同步清理检查点、索引、证据关系和派生记忆 |
| 自动学习成本增加 | 默认关闭；按 revision 去重；限制频率、分块和输出数量 |
| 数据迁移失败 | 事务化、幂等、备份副本验证；失败时不删除旧表 |
| 检查点越积越多 | 同 revision 去重；保留最近检查点和必要历史；清理前确认可从原始日志重建 |
| 记忆注入挤占上下文 | 设置总预算、相关性阈值和去重；无关时不注入 |
| 模型把历史资料当指令 | 统一作为 untrusted data 标记；绝不进入系统约束区 |

## 16. 明确不做的事情

- 不重写现有 Agent 会话管理或模型调用链。
- 不引入新的向量数据库、图数据库或外部记忆服务作为本轮前置条件。
- 不直接安装 pi-vcc、pi-smart-compact、pi-observational-memory 等第三方插件。
- 不复制整份原始对话到记忆数据库。
- 不让模型自动批准自己生成的记忆。
- 不将历史命令转换为可执行动作。
- 不进行大规模 UI 重构，不新增复杂的记忆管理工作台。
- 不以压缩率为唯一指标，不删除为了节省 Token 而删除关键证据。
- 不顺手重构与本计划无关的模块。

2. 先完成 P0 审计并给出实际文件清单、数据流和测试基线；若发现本计划与现有代码不一致，先修订实施步骤并说明原因，不得硬套假设。
3. 按 P1 → P2 → P3 → P4 → P5 顺序实施，每阶段完成后运行对应测试。
4. 优先小步、增量、可回滚修改；不得删除现有历史数据或破坏旧 Memory 条目。
5. 所有新增 IPC、Agent 工具和数据库字段都要遵循现有类型、校验、Main ownership 和安全边界。
6. 不安装大型依赖；确需依赖时先说明现有实现为何不足、包体/维护成本和许可证，再选择最小方案。
7. 不以 mock 结果代替真实本地 SQLite 集成测试；不调用真实业务集群或付费模型完成测试。
8. 完成后提供逐项验收表，明确哪些通过、哪些未通过、哪些因环境限制未执行。

**最终验收原则：压缩可以减少模型需要携带的上下文，但不能减少墨巡对原始历史的可追溯性；记忆可以帮助理解和延续工作，但不能把未经验证的历史推断变成当前事实。**
